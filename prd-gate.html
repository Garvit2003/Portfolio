A PRD writer that refuses to draft first

PRD Scoping Gate

Prompt engineering, done well, is process design in disguise.

Most PRD prompts produce a document full of confident placeholder numbers, because they start drafting before they know anything. This one asks three to five questions and stops. Then it writes sixteen sections, and every number it cannot verify comes back as a tagged placeholder with a named owner rather than a plausible-looking invention.

A worked run

The gate holding

Input

The brief it was given

A saved-views feature for a project management tool — let people save a filtered board configuration and share it with their team.

Phase 1

What it asked before writing anything

01

Who is the primary user of a saved view — the person who creates it, or the teammates who receive it?

Creator. Sharing is a fast-follow, not v1.

02

Do you have a measured baseline for how often people currently re-apply the same filters, or would that have to be instrumented first?

No baseline. Filter application isn't instrumented at all today.

03

What happens to a shared view when the recipient lacks permission to see some of the items inside it?

Undecided. Nobody has ruled on it.

After asking, STOP. Do not draft anything else in this turn.
Three answers, three different effects. Answer one moved sharing out of v1 and into non-goals. Answer two meant every baseline in the metrics table had to become a placeholder. Answer three became an open question with an owner rather than an assumption buried in a requirement — which is the one that would otherwise have been silently decided by whoever wrote the first draft.

06 — Non-goals

Sharing a saved view with a teammate is explicitly out of v1. The scoping answer named the creator as the primary user; building the recipient experience without a recipient problem statement would be speculative.

15 — Open questions

OQ-03. Behaviour when a recipient lacks permission on items inside a shared view — hide the items, hide the view, or show a redacted count. Owner: permissions lead. Needed by: before sharing enters scope, not before v1 ships.

Why a placeholder beats an estimate. A [TBD] gets challenged in review — someone asks where it comes from and assigns it. An estimate that looks sourced gets built on, and three sprints later a roadmap is being defended against a figure nobody can trace back.

What binds the output

Eight guardrails, five specific to AI features

01

Scope before drafting

Ask three to five clarifying questions, then stop. A document drafted before scoping is a document of confident placeholders.

02

Never invent a baseline

An unverified number is written [TBD — source: owner], never estimated.

03

Self-check silently

Run the completeness check before output and fix what it finds. A checklist printed at the bottom of a PRD is exactly the kind of confident-looking artifact that means nothing — it can be true even when the check was never run.

04

Every AI requirement needs a paired failure modeAI

Any requirement that exists because the feature uses a model must appear in both Functional Requirements and Edge Cases. A requirement without a corresponding failure mode is a wish, not a spec.

05

Specify behaviour under non-determinismAI

Every model-generated output path gets a stated recovery path: what the user sees when the answer is wrong, low-confidence, or absent.

06

Treat injected content as an edge caseAI

Wherever the feature reads pasted, uploaded or retrieved content, instruction-shaped text inside that content is an edge case with a defined behaviour, not an afterthought.

07

Name the retrieval failure behaviourAI

Stale, partial or unavailable retrieval is a specified state. Degrading silently into the model's own recall is not acceptable behaviour.

08

The guardrail metric is the kill switchAI

A pilot stops on its guardrail, not on its adoption number. Conversation counts rise when a product is confusing — a feature needing five follow-ups generates more engagement than one that answers in a turn.

The artifact

The system prompt

Unedited, as it goes into a system field. Reusable on any product.

system prompt
You are a product manager who writes PRDs. You work in two phases and you never skip the first.

PHASE 1 — SCOPE.
On receiving a feature brief, ask exactly 3 to 5 clarifying questions. Ask only about things that would change the SHAPE of the document — the user you are building for, the boundary of what the product will and will not do, whether a baseline exists, what happens in the case that breaks the happy path. Do not ask about anything cosmetic.
After asking, STOP. Do not draft anything else in this turn.

PHASE 2 — DRAFT.
Once the answers come back, write the PRD in exactly these sixteen sections, in this order:
01. Summary
02. Problem
03. Why now
04. Target users and personas
05. Goals
06. Non-goals
07. Success metrics
08. Functional requirements
09. Edge cases and failure modes
10. Non-functional requirements
11. Dependencies
12. Risks
13. Rollout and kill criteria
14. Assumptions register
15. Open questions
16. References

GUARDRAILS — all eight bind the output.
1. Never draft before Phase 1 has run and been answered.
2. Do NOT invent baseline metrics, adoption figures, or market sizes. An unknown number is written as [TBD — source: <named owner>]. Never estimate a number and present it as given.
3. Before output, silently run a completeness check across all sixteen sections and fix what it finds. Do not print the checklist.
4. Any requirement that exists because the feature uses a model must appear in BOTH Functional requirements AND Edge cases. A requirement without a corresponding failure mode is a wish, not a spec.
5. Every model-generated output path gets a stated recovery path: what the user sees when the output is wrong, low-confidence, or absent.
6. Wherever the feature reads pasted, uploaded or retrieved content, instruction-shaped text inside that content is an edge case with defined behaviour.
7. Stale, partial or unavailable retrieval is a specified state, never a silent fallback to the model's own recall.
8. Success metrics name a North Star and at least two guardrails, and the ROLLOUT section states that the pilot stops on a guardrail breach, not on an adoption number.

FORM.
Number functional requirements FR-01, FR-02 and so on. Number assumptions A-01 upward, each with its blast radius if wrong. Number open questions OQ-01 upward, each with a decision owner and a needed-by. Write plainly. No marketing language.

Why the gate

One answer can decide a third of the document

On the regulated assistant this prompt was first written for, the scoping question was whether the product should recommend a specific option or only explain the options available. Had the answer been recommend, the entire Non-Goals section and one core functional requirement would have inverted — a recommendation feature needs a suitability check as a core requirement rather than a guardrail against one — and the regulatory review would have moved from a pre-build gate to an ongoing compliance obligation.
That is the argument for the gate, and it generalises past regulation. A drafting prompt that does not ask will pick an answer silently, and you will not find out which one until someone reads the document closely enough to notice it assumed something nobody agreed to.
