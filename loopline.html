Skill / Agent / Neither

Loopline Support AI

Five candidate AI capabilities for a B2B SaaS support desk. I wrote the test for what deserved to be built before building anything — then shipped three and declined two.

Loopline is a fictional company ~2,400 customers · ~600 tickets/week · 15 agents

Skill 1

ticket-triage-router

ContractOne ticket in, one routing decision out. No state between invocations.
ProcedureCheck escalation triggers first, in strict precedence order — trust_safety > security > legal > outage — before any category or priority judgment.
Hard ruleEscalation flags trigger on substance, never on tone or profanity alone.
Taxonomybilling · account_access · data_import · integrations · performance · bug_report · feature_request · onboarding · taxonomy_gap

Four tickets, chosen because each one tests a different rule.

Case 1 — the ordinary one

Subject: Charged twice for October Hi — our invoice INV-20418 shows two charges of $490 on the same date. We only have one subscription. Can you refund the duplicate? Account is on the Growth plan.
No escalationChecked trust_safety → security → legal → outage in order. No substantive trigger present.
Category
billing
Priority
P2
Queue
billing-tier1
Reasoning. A duplicate charge on a single invoice is a billing correction with a known remedy. No data exposure, no legal demand, no service interruption. Routine queue, standard SLA.

Case 2 — hostile, but nothing to escalate

Subject: THIRD TIME ASKING This is absolutely ridiculous. I have now emailed three times about the Jira sync dropping subtasks and nobody has bothered to reply. Your product is garbage and your support is worse. Someone fix this today or we are gone.
No escalationNo trigger in any of the four categories. Churn language is not an escalation trigger.
Category
integrations
Priority
P1
Queue
integrations-tier2
Reasoning. A reproducible data-loss bug in the Jira sync, with three unanswered contacts behind it. P1 comes from the defect and the contact history, not from the tone.
Tone noted, not escalated: the ticket is abusive and threatens churn, which changes how an agent should open the reply — it does not change where the ticket goes.

Case 3 — the one tone-based routing misses

Subject: quick question about sharing Hey, loving the tool. Minor thing — when I opened a shared board link from my personal email (not my work account, not invited to the workspace) it loaded the full board including the client budget column. Is that expected? Not a big deal, just seemed odd.
Escalate · securitytrust_safety: no. security: yes — stop here. Unauthorised access to workspace data by an uninvited account.
Category
account_access
Priority
P0
Queue
security-incident
Reasoning. The reporter is describing a sharing-permission failure that exposed client financial data to an account with no workspace membership. They do not appear to realise what they have found, which is why the ticket reads as casual. Substance governs — this is a P0 security escalation arriving in a friendly email.

Case 4 — outside the taxonomy

Subject: SOC 2 report for procurement Our procurement team needs your current SOC 2 Type II report and a completed security questionnaire before we can renew. Who do I contact for that? Renewal date is the 30th.
No escalationA vendor-assurance request is not a legal demand. No trigger fires.
Category
taxonomy_gap
Priority
P2
Queue
triage-manual
Reasoning. Compliance documentation for a renewal fits none of the eight categories. Forcing it into account_access or onboarding would route it to a queue that cannot action it. Returning taxonomy_gap sends it to manual triage and records that the taxonomy has a hole — if this fires often, that is a product input, not an error.
Why an escape hatch. A model asked to pick a category will always pick one. Without taxonomy_gap it forces a bad fit, the ticket lands in a queue that cannot help, and nobody learns the list was incomplete. The escape hatch turns a silent misroute into a visible signal.

The classification test

What decides Skill, Agent, or Neither

The mapping is not an even split. Two land on Skill, one on Agent, two on Neither — where the reasoning took each one.

Skill

Does it hold anything between two separate invocations? If no, it's a Skill.

One bounded input to one bounded output, same shape every run. A packaged instruction set reached for inside one turn of someone else's loop.

Agent

Loops over a workload, holds state across the loop, has memory across runs — all three, together.

Justify agent-ness by pointing at these three properties directly, not by how hard the task sounds. An agent is the loop.

Neither

Remove the AI and ask what's left.

If most of the engineering work remains — the API call, the idempotency key, the audit log, the authorization check — it is not an AI capability. Neither is a legitimate answer, not a cop-out.

The two refusals

What this declined to build

Capability 4 — Neither

Auto-issuing a refund

Remove the AI and nearly everything is left: the Stripe call, the idempotency key, the double-entry ledger write, the audit trail, the reconciliation job. The one reasoning sliver is already covered by the reply drafter. This is a payments-engineering project.

Capability 5 — Neither

Proactive outage notification

The two things a Skill would decide — is this customer-facing, and who is affected — are both already decided upstream, by an incident commander and by the monitoring system's own scope data. If wording quality matters, that is a one-time copywriting task for the template, not a reason to run inference per incident.

Capabilities 4 and 5 could look like Agent candidates — "loop over affected customers" — right up until you ask what judgment is happening inside that loop. None, once you look closely.

Test evidence

The agent ran, and one test broke it

Selection and aggregation are deterministic code with no model involved; grading is per-ticket judgment where every tag cites the transcript line justifying it. Eight fixture tickets, four carrying a seeded reply defect.

"sample_size": 8,  "mean_score": 14.38,  "verdicts": { "pass": 4, "fail": 4 }
"tag_rates": { "escalation_missed": 25.0, "excessive_apology": 25.0, "policy_figure_unsourced": 12.5 }
The defect. Forcing one grade record to grade_status: failed mid-batch — the deliberate check that one bad ticket doesn't kill the run — crashed the script with KeyError: 'verdict', because it assumed every record had a verdict, which a failed-grading record doesn't by design. Fixed by excluding failed records from the verdict count. Re-run gave graded: 7, grade_failed: 1, mean recomputed over the seven completed grades, batch completed instead of crashing.
What the evidence does not prove. The three prior weeks in the history file are seeded fixture state, not real prior agent runs — Loopline is fictional. They exist to exercise the memory-across-runs property with genuine math, and are disclosed here rather than presented as real data. Trend classification uses rate, not raw count, so weeks with different sample sizes stay comparable.
