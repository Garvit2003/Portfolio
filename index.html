QueryPilot: ask your database a question in plain English

Business users shouldn't need SQL to get an answer. QueryPilot turns a question into SQL and checks it. You get the answer, an explanation, and every assumption it made. The rule I designed it around: the AI proposes the SQL; plain code decides whether it may run.

    Meetings produce promises. Nobody closes them.

    Fireflies extracts commitments from meetings, but at 14 days only 28% are resolved. I designed two features. Claim assigns ownership only when someone confirms it, never automatically. Close resolves items from evidence, asks a person once a week only when it can't, and offers a first-class "not doing this" exit.

    Research
    Ten semi-structured interviews. I didn't ask about habits. I asked each person for one thing they'd promised in a recent meeting and traced what happened to it. Ten against a guidance of fifteen, engineering-heavy, with no buyer in the sample.
    Sizing
    I split the unresolved 72% by what actually blocks closure: no owner, done but never recorded, no honest exit, context switching, or genuine work still pending. Roughly three-quarters of it is a state-and-ownership problem, which software can fix.
    Metrics
    North Star: 14-day honest closure, 28% → 45% target. Five key results, six guardrails and a seventeen-event instrumentation spec. The guardrail I'd read first alarms when the drop rate falls below 5%: if nobody drops anything, the exit doesn't feel safe.

    D-02Vibe coding for PMsWorking softwarePython · tested

    Most "AI features" are workflow problems in disguise.

    For a fictional B2B support team, I classified five candidate AI capabilities as a Skill, an Agent, or Neither, then built and tested each on its own. A Skill holds nothing between runs. An Agent loops over a workload, holds state across the loop and remembers across runs, all three at once. For Neither, remove the AI and see what's left. If most of the work remains, it isn't an AI problem.

    D-03LLMs & RAGBankingSystem prompt + 16-section PRD

    Prompt engineering, done well, is process design.

    I wrote a reusable system prompt that turns an LLM into a PRD writer, then used it unedited to specify Vault Advisor, a grounded assistant for the deposit journeys I work on. It informs but never transacts. It never recommends a product, tenure or amount, because that crosses into investment advice.

    The gate holdingA real run, start to stop

    Brief given: a saved-views feature for a project management tool — let people save a filtered board configuration and share it with their team.

    01

    Who is the primary user of a saved view — the person who creates it, or the teammates who receive it?

    Creator. Sharing is a fast-follow, not v1.

    02

    Do you have a measured baseline for how often people re-apply the same filters, or would that have to be instrumented first?

    No baseline. Filter application isn’t instrumented at all today.

    03

    What happens to a shared view when the recipient lacks permission to see some of the items inside it?

    Undecided. Nobody has ruled on it.

    After asking, STOP. Do not draft anything else in this turn.

    What those answers did to the documentThree answers, three different effects
    Success metricBaselineTarget
    Time to the view the user wanted[TBD — analytics lead]−40%
    Repeat filter application per user, per week[TBD — analytics lead]−50%
    Views created per active board[TBD — analytics lead]Guardrail, not a goal
    Answer 1 → Non-goals
    Sharing moved out of v1. Building a recipient experience without a recipient problem statement would be speculative.
    Answer 2 → Metrics
    No baseline exists, so every baseline became a tagged placeholder with an owner rather than an estimate.
    Answer 3 → OQ-03
    Behaviour when a recipient lacks permission — hide the items, hide the view, or show a redacted count. Owner: permissions lead. Needed by: before sharing enters scope. Without the gate, whoever drafted first would have decided this silently.
    Scoping gate
    The prompt asks three to five questions, then stops. It drafts nothing until they're answered. One answer decided the shape of about a third of the PRD.
    No invented data
    Unknown numbers are written as [TBD — source: owner]. The PRD contains zero invented numbers.
    Unit economics
    I modelled cost per conversation against the containment rate at which the assistant pays for itself.
    Kill switch
    The pilot stops on the guardrail metric, not on adoption. Every LLM-driven requirement has a matching failure mode.

    "A requirement without a corresponding failure mode is a wish, not a spec."

    The prompt itself
    You are a product manager who writes PRDs. You work in two phases and you never skip the first.

PHASE 1 — SCOPE.
On receiving a feature brief, ask exactly 3 to 5 clarifying questions. Ask only about things that would change the SHAPE of the document — the user you are building for, the boundary of what the product will and will not do, whether a baseline exists, what happens in the case that breaks the happy path. Do not ask about anything cosmetic.
After asking, STOP. Do not draft anything else in this turn.

PHASE 2 — DRAFT.
Once the answers come back, write the PRD in exactly these sixteen sections, in this order:
01. Summary                        09. Edge cases and failure modes
02. Problem                        10. Non-functional requirements
03. Why now                        11. Dependencies
04. Target users and personas      12. Risks
05. Goals                          13. Rollout and kill criteria
06. Non-goals                      14. Assumptions register
07. Success metrics                15. Open questions
08. Functional requirements        16. References

GUARDRAILS — all eight bind the output.
1. Never draft before Phase 1 has run and been answered.
2. Do NOT invent baseline metrics, adoption figures, or market sizes. An unknown number is written as [TBD — source: <named owner>]. Never estimate a number and present it as given.
3. Before output, silently run a completeness check across all sixteen sections and fix what it finds. Do not print the checklist.
4. Any requirement that exists because the feature uses a model must appear in BOTH Functional requirements AND Edge cases. A requirement without a corresponding failure mode is a wish, not a spec.
5. Every model-generated output path gets a stated recovery path: what the user sees when the output is wrong, low-confidence, or absent.
6. Wherever the feature reads pasted, uploaded or retrieved content, instruction-shaped text inside that content is an edge case with defined behaviour.
7. Stale, partial or unavailable retrieval is a specified state, never a silent fallback to the model's own recall.
8. Success metrics name a North Star and at least two guardrails, and the ROLLOUT section states that the pilot stops on a guardrail breach, not on an adoption number.

FORM.
Number functional requirements FR-01, FR-02 and so on. Number assumptions A-01 upward, each with its blast radius if wrong. Number open questions OQ-01 upward, each with a decision owner and a needed-by. Write plainly. No marketing language.
    D-04Problem framingQuick commerce11 pages

    The basket isn't small because the cart is quiet.

    The brief was to raise Zepto's average order value. The usual comparison puts Instamart far ahead, but the three companies report on three different bases. I restated them on one basis before touching the product.

    Check the ruler

    Control group
    Blinkit had already run the cart-nudge playbook across its dark stores, and its net AOV went ₹521 → ₹525 → ₹518. The standard fix had been tried at scale, and AOV went down.
    Root cause
    Five whys led to dark-store shelf allocation. The basket ceiling comes from the same density model that gives Zepto its cost advantage.
    Framework
    I cut fifteen ideas to three. RICE ranked the safe idea first, and I overrode it in writing. Effort sits in the denominator, so RICE under-ranks anything that needs a new capability.
    D-05Tech & system designEdTech14 pages

    A match on topic isn't a match on readiness.

    Two learners searching "machine learning" can be in completely different places. Pathwise tags every course against a skill graph with prerequisites. It tracks each learner's mastery and recommends the shortest path to their stated goal.

    Why it matters
    Average MOOC completion sits around 6.8%, and even learners who intend to finish complete under half the time.
    Spec
    Fifteen user stories, ten functional requirements and fourteen non-functional ones. Each NFR has a verification method, from a chaos drill that kills the ranker mid-traffic to a consent audit.
    Trade-off
    Maximum personalisation and a 400ms p95 feed can't both hold forever. I chose event-triggered freshness: a full re-rank on a completion, a retaken test or a goal change, plus a falsification test for that choice.
    Architecture
    A modular monolith, with the intelligence layer split out from day one because its scaling profile and its release cadence both differ from the rest.
    D-06Growth & monetisationTravel14 pages

    Airbnb can't out-hire MakeMyTrip. It has to out-product it.

    Indian group trips get planned off-platform, in WhatsApp threads, and only about one homestay in eight is registered. I designed a product-led loop for each of those gaps and tested both against one rule: does the output become the input without new spend?

    Loops
    Trip Circles turns group planning into invitations. Host Formalisation gives informal hosts a vernacular, DigiLocker-backed path onto the platform.
    Kill criteria
    Abandon Trip Circles if fewer than 1.5 new accounts are created per board. Drop the vernacular path if under 15% of new hosts adopt it.
    Refused
    Matching the competitor's commission, which would only compress Airbnb's own margin. The revenue model widens instead.
    Disclosed
    No primary interviews and no MVP testing yet. The roadmap's first phase exists to close that.

    E-01
